Business Context

Domain: Automotive ECU Testing

What is a Test Bench?

A physical workstation that simulates a vehicle's electronic network to test ECUs (Electronic Control Units) before deployment into a real car.

The MTF Framework

The Modular Test Framework is a proprietary test automation platform that orchestrates communication between test software and hardware devices on the bench.

To run, MTF requires a configuration file: config.yaml

Devices on a Test Bench

CAN Interface LIN Card Ethernet Adapter Relay Board Power Supply Battery Simulator Serial Port Analog Device Electronic Load

Stakeholders: Test engineers who configure benches daily and need to produce a valid config.yaml to start any test session.

Business Context

The Problem

Manual YAML Authoring

Engineers wrote config.yaml entirely by hand — a complex, nested YAML file with strict MTF-specific syntax.


  • Invalid field names go undetected until runtime
  • Incompatible channel mappings cause test failures
  • Duplicate channel IDs silently corrupt configs
  • No tooling assistance — pure text editing
  • Slow onboarding for new engineers

Sample of what they wrote manually

Channels:
  CAN_ECU:
    Type: CANChannel
    Id: 1
    HWChannel: 0
    Mapping: Peak_USB
# dozens more channels...
Hardware:
  Peak_USB:
    Type: CANInterface
    Device: PCAN_USBBUS1
# no validation, no autocomplete

A single typo in a field name causes the entire test session to fail — discovered only at runtime.

Defined Solution

Channel Configuration Manager

A VS Code Extension

Integrates directly into the engineers' existing IDE. Activated automatically when an MTF.yaml file is detected in the workspace.


Core Capabilities

  • Form-based CRUD for all channel types
  • Mapping engine with compatibility validation
  • Automatic config.yaml generation
  • Import existing configurations
  • AI validation (Gemini API)
  • MTF knowledge chatbot (local Ollama RAG)
  • Hardware diagram visualization

Key Design Decisions

Singleton Webview Panel
One persistent React app injected into VS Code — preserves state, no re-renders on tab switch.

SOLID Principles
SRP applied throughout: ConfigGenerator only serializes, ConfigValidator only validates, ConfigImporter only handles I/O.

Two-bundle Webpack
Extension and Webview are built separately — isolates Node.js APIs from browser APIs.

Domain Model

Four Core Concepts

① Logical Channel

The abstract communication endpoint seen by the test software. Each one has a protocol type (CAN, LIN, Ethernet…) and a unique numeric ID.

CAN/CANFD LIN Ethernet FlexRay IO / Serial / PS

② Hardware Channel

The physical device on the test bench that handles the actual communication signal.

CANInterface EthernetAdapter LINCard Relay / PSU / BTS

③ Mapping

The link between a logical channel and a hardware device. Subject to protocol compatibility rules — a CAN channel can only map to a CAN interface, not an Ethernet adapter. One logical → at most one hardware.

④ Framework Config

Runtime parameters for the MTF framework itself: Publisher (execution threading), Tracers (PCAP / ASCII logging), Ethernet Config, and Diagnostics (UDS/OBD).

Domain Model — Detail

① Logical Channels

What is a Logical Channel?

The abstract endpoint the test software communicates with. It represents a communication protocol bus — completely decoupled from the physical hardware.


Common Fields (all types)

name Unique identifier — no spaces, no leading digit
channelId Unique positive integer — required by MTF
loggingName Name used in test logs for traceability
tracerName Links channel to a PCAP/ASCII tracer
alias[ ] Alternative names for the channel

All Supported Types

CAN / CANFD Controller Area Network bus — most common in automotive
LIN Local Interconnect Network — sensors & actuators
ETHERNET IP-based automotive Ethernet (SOME/IP, DoIP)
FLEXRAY Deterministic bus — safety-critical systems
IOINPUT Digital/analog input signal
IOOUTPUT Digital/analog output signal
SERIAL Serial port communication
PS Power supply channel
BRIDGE Protocol bridging channel

② Hardware Channels

What is a Hardware Channel?

A physical device plugged into the test bench. It handles the actual signal — transmitting and receiving on the bus, switching relays, sourcing voltage, etc.

Domain Model — Detail

③ Mapping & Compatibility Rules

Compatibility Matrix

The system enforces which logical → hardware combinations are valid:

CAN/CANFD→CAN_INTERFACE only
ETHERNET→ETHERNET_ADAPTER only
LIN→CAN_INTERFACE or SERIAL_PORT
FLEXRAY→CAN_INTERFACE or ETHERNET_ADAPTER
IOINPUT/OUT→RELAY, HID_RELAY, ANALOG, BTS, HH_LOAD
PS→GENESYS_PS or MANSON_PS only
SERIAL→SERIAL_PORT only

Business rule: Each logical channel → at most 1 hardware channel. Violation throws an error immediately at mapping creation time.

Mapping Parameters

Each mapping carries protocol-specific metadata written into the YAML:

hwChannel Port number on the hardware device
operationMode CAN mode (Normal, ListenOnly…)
keySlot / nodeType FlexRay slot and node configuration
btsFunction BTS Revo measurement function
initValue Initial state for IO output channels
wakeUpCluster FlexRay wake-up cluster flag
staticChannel Mark channel as static/dynamic
Domain Model — Detail

④ Framework Configuration

Publisher Config — Execution Model

Controls how MTF schedules channel communication at runtime.

SingleThreaded — All channels share one execution thread. Simple, lower overhead. Default choice.

MultiThreaded — Each channel group runs on its own thread. Better performance for high-throughput benches. Requires defining channelsGroups.

Ethernet Config

VLAN ID / Priority802.1Q tagging
ServerPorts / ClientPortsPort ranges for SOME/IP services
InnerTags / OuterTagsDouble VLAN tag stacking

Tracers — Logging Subsystem

Each logical channel can reference a named tracer. Multiple channels can share a tracer.

PCAP Tracer — Captures raw network traffic to .pcap files. Configurable: logging type (MultipleAdapterMode / PerformanceMode), timestamp precision (Microsecond / Nanosecond), buffer & file settings.

→ Opened in Wireshark for post-test analysis

ASCII Tracer — Captures decoded messages to a human-readable text file. Useful for quick debugging without Wireshark.

Diagnostics Config

UDS (ISO 14229) and OBD-II diagnostic parameters — target ECU address, tester address, response timeout. Required for diagnostic test cases.

Key Feature

Config Generation Pipeline

Validation (before generation)

  • Name format: /^[A-Za-z_][A-Za-z0-9_\-]*$/
  • Unique positive integer channelId
  • No duplicate channel names
  • At least one mapping per config
  • Mapping compatibility (protocol match)
  • Tracer references exist in framework config
  • Alias naming rules same as channel names

All errors shown in UI before the YAML file is touched. Zero silent failures.

Generation Flow

ConfigValidator.validate()
↓
Serialize logical channels
↓
Serialize hardware channels
↓
Serialize mappings + framework
↓
Apply MTF YAML formatting
↓
Write config.yaml ✓
Key Feature

AI Validation (Gemini Pro)

Two-Layer Validation

Layer 1 — Local Rules (always runs)
Fast, offline, deterministic. Catches structural and naming errors.

Layer 2 — Gemini AI (when key configured)
Semantic analysis: detects protocol mismatches, missing recommended fields, best practice violations.


What Gemini analyzes

  • Protocol incompatibilities in mappings
  • Suboptimal parameter configurations
  • Missing optional but recommended fields
  • Best practice violations
  • Any other anomalies in the YAML

Output Structure

{
  "isValid": true,
  "errors": [
    "CAN_ECU mapped to LIN hardware"
  ],
  "warnings": [
    "Baudrate not specified for CAN_ECU"
  ],
  "suggestions": [
    "Add loggingName for traceability",
    "Consider enabling PCAP tracer"
  ]
}

Graceful degradation: falls back to local validation if no API key is set, with a clear warning message.

Key Feature

MTF Agent — Local RAG Chatbot

RAG Pipeline (fully local)

① Embed question → nomic-embed-text
↓
② Hybrid retrieval from knowledge base
65% vector cosine + 35% keyword + graph expansion
↓
③ Build grounded system prompt (top 5 chunks)
↓
④ Stream answer via llama3.2 (Ollama)

Knowledge Base

Pre-built JSON file containing embedded chunks of the MTF documentation:

  • Each chunk has: title, section, content, summary, keywords
  • relatedIds — graph links to related chunks
  • Pre-computed embeddings (no runtime cost)
  • Importance scores (high / medium / low)

100% offline — no data leaves the machine. Engineers can ask: "What fields are required for a CAN channel?" and get an accurate, sourced answer.
