Slide 1

AI Architecture Schema

Visual summary of the AI phase components and how validation, retrieval, generation, and safety interact.

Webview UI MessageHandler AIValidator / LocalValidator RoutedMtfAgent KnowledgeBase OllamaClient Guardrails
Speaker Notes

In this first slide, I present the global architecture of the AI module integrated into the VS Code extension. The interaction starts from the webview UI, where the developer can either launch validation actions or ask questions to the documentation agent. All requests are received by MessageHandler, which acts as the central orchestration layer between the user interface and the backend services. The first branch is the validation branch. Here, AIValidator serves as the entry point, but the effective validation logic is performed by LocalValidator, which checks mandatory fields, invalid identifiers, and duplicate mappings. The second branch is the agent branch. In this branch, RoutedMtfAgent prepares the request, builds the prompt, and enriches it with the current workspace context, such as the active configuration, diagnostics, and YAML content. Then, the KnowledgeBase retrieves the most relevant chunks from the local MTF documentation, while OllamaClient provides both the embedding step and the final local language model generation. Before returning anything to the user, a guardrail layer verifies that the answer is supported by evidence and that no unsafe or unsupported YAML modification is suggested. So the key architectural idea is simple: deterministic validation first, grounded generation second, and guarded delivery at the end. Transition to the next slide: now that the static structure is clear, I will move to the dynamic view and show how a user question is processed step by step at runtime.

Slide 2

Agent Logic Flow

Visual summary of the runtime sequence followed by the support agent from the first question to the final verified answer.

Context build Intent routing Hybrid retrieval Grounded generation Guarded delivery
Speaker Notes

This second slide explains the runtime logic of the MTF support agent. The process starts when the user enters a question in the chat panel. The system then builds the context by collecting the useful runtime information available in the workspace, including the current configuration, YAML content, and any validation diagnostics. After that, the agent performs intent routing. This step is important because it decides whether the request is mainly a support question, an error-analysis request, or a mixed case. Once the intent is identified, the retrieval phase begins. The agent searches the local documentation base using semantic retrieval and related chunks in order to gather evidence that is relevant to the question. Based on that evidence, the generation phase produces a grounded answer through the local language model. In other words, the model does not answer blindly; it answers using the retrieved documentation and the current configuration context. Then comes the safety checkpoint. At this stage, the system verifies three things: first, that the answer is backed by evidence; second, that it does not make unsupported claims about parse errors or diagnostics; and third, that it does not suggest unsafe YAML rewrites. If the answer passes these checks, it becomes a verified answer and is streamed progressively back to the webview, together with the associated sources. This runtime flow shows how the architecture from the previous slide is transformed into a reliable interaction pipeline for the user. Transition to the conclusion: with these two views, the static architecture and the runtime flow, we can clearly understand how the AI module remains local, grounded, and safe while assisting the developer.
